以前写代码是打开编辑器，现在很多时候是打开对话框。用久了会发现，真正让人难受的不是模型不够强，而是需求给得太碎。

想加一个功能，随口说一句，模型几分钟就写完了。看着没问题，跑起来也能用。然后你继续补：密码要加密、错误提示要统一、参数要校验、状态要兜底。几轮下来，功能确实齐了，但原来能跑的接口开始报错，变量被覆盖，逻辑被改得面目全非。最后一下午都在回滚和修 Bug。

这种开发方式，海外开发者给它起了个名字：Vibe Coding，凭感觉编程。没有前置规划，没有需求文档，也没有任务拆解，全靠脑子里模糊的感觉，边聊边改。

## Vibe Coding 不是不能用

小脚本、临时工具、周末 Demo，用 Vibe Coding 非常舒服。不用画流程图，不用想架构，脑子里有个大概，模型就能帮你落地。这个场景下，它的效率确实高。

问题出在项目变大之后。Vibe Coding 很像口头需求对接外包：你随口说做一个功能，做完想起一个细节，改完又想起一个逻辑，全程没有完整需求，也没有全局视图。模型每次只看到“当前这一句话”，它不知道你整体想做成什么样，也不知道哪些旧逻辑不能动。

于是就会出现很典型的情况：写第五步的时候干掉了第一步，补新功能的时候破坏了旧功能，改一处代码引发一串连锁 Bug。不是模型突然变笨了，而是它拿到的信息本来就是碎的。

## Spec Coding：先把话说明白

Spec Coding，也就是规约驱动开发，核心只有一句话：先把要做什么、为什么做、怎么做、拆成什么讲清楚，再让模型写代码。

它不是让 AI 先写一份漂亮的文档，而是把人和 AI 的协作方式从“边聊边猜”换成“对着同一份东西做事”。我现在会把它拆成四步：

1. **需求**：只谈业务。功能目标、使用场景、用户角色、验收标准，先不出现框架和数据库。
2. **方案**：需求定了，再确定技术栈、模块拆分、数据表、接口。
3. **任务**：把方案拆成一条条独立、可执行、不冲突的小任务。
4. **实现**：前三步对齐之后，再让模型批量写代码。

这四步听起来像瀑布流，其实不是。规约是活的，需求变了就改需求，方案错了就改方案，任务拆错了就重拆。区别在于，错误被拦在写代码之前，而不是等系统崩了再返工。

## 一个很实际的差别

Vibe Coding 的对话是线性的：你说一句，模型改一处。Spec Coding 的对话是围着同一份规约转的：模型先读需求，再读方案，最后只做当前任务。

这两种方式在短对话里差别不大，但项目一旦跨天、跨会话，差距就出来了。你不会记得三天前随口说过什么，模型更不会。把关键决策写进 `spec.md`、`plan.md`、`tasks.md`，下一次打开项目时，人和模型都能从同一页继续。

GitHub 的 `spec-kit` 把这套流程做成了命令：先生成项目宪法，再生成需求规约、技术方案、任务清单，中间可以澄清歧义，最后做一致性检查，确认需求、方案、任务没有互相打架，再进入实现。工具本身不复杂，值钱的是它强迫你在动手前把问题想清楚。

## 不是所有项目都值得

Spec Coding 也有成本。写规约要时间，维护规约也要时间。一次性脚本、临时 Demo、小玩具，直接 Vibe Coding 更划算；长期维护的项目、业务复杂、需要多人或多轮迭代的工程，才值得先把规约写出来。

我现在大概是这样分的：能在一个下午扔掉的东西，随便聊；要留在仓库里、以后还会打开的东西，先写一份简短的 spec。哪怕只有半页，也比没有强。

## 最后

AI 把“写代码”这件事的门槛拉低了很多，但项目能不能长期维护，还是取决于需求有没有讲清楚、边界有没有划清楚、决策有没有留下来。

Vibe Coding 拼的是模型当下的能力，Spec Coding 拼的是开发者把问题说清楚的能力。前者很爽，后者更稳。两者不是敌人，关键看你现在做的是玩具，还是要留下来的东西。
