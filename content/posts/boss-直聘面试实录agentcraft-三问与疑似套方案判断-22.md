九月初在 BOSS 直聘上投了一家公司，广州她格人工智能科技。对方约了线上聊，我以为是常见的“先介绍一下自己”，结果三个问题一路往实现细节里钻。

前两个我答完了，第三个停住了。

## 第一问：讲一个你真正做过的 AI 项目

面试官问得很完整：项目解决什么问题、我负责哪块、用了什么模型和技术栈、最后上线效果怎么样。

我讲的是实习时负责的 AgentCraft。简单说，它是一个多租户的 Agent 工作台，把专家人设、方法论、Skill 和 MCP 工具打包成可以发布的 AI 专家，也支持用户自带密钥调用。做它的起因是，很多领域专家的经验散在提示词和笔记里，没法复用；普通用户又很难自己拼出一套能用的垂直智能体。

我主要负责两块。一块是 Agent 运行时，基于 pi agent-core 做上层平台开发，任务启动时把配置注入进去，再用任务级快照把这一轮的配置冻住，避免跑到一半被人改掉。另一块是 SSE 流式链路，把 MCP 工具的注册、授权、执行、回传这条链路打通，前端能看到“正在调用某个工具”。

后端是 FastAPI + SQLAlchemy + Alembic，数据库当时是 SQLite，后来在 PostgreSQL 上重建；前端 React + Vite，Docker 部署，测试用 pytest，Playwright 做辅助验证。开发过程中也用了一些 coding agent 帮我跑流程。

这个项目没有公网上线，它是公司课程教材的主线示范项目，交付目标是可复现的 MVP 和配套实验材料。

## 第二问：RAG、工具调用和多轮状态

第二个问题一下子抛了四个点：文档切片、向量检索、重排、多轮状态。

我先说清楚：这个项目不是 RAG 架构，所以切片、向量、重排都没有做。与其硬凑，不如先把不适用的部分排除掉。

工具调用这块，我基于 MCP 把 HTTP 和 stdio 两种链路都跑通了。先做工具注册和发现，读取 MCP 服务暴露出来的工具列表，绑定到专家上；对话里由模型决定要不要调用，pi 负责解析模型输出的工具调用请求，我再校验任务快照，确认这次调用被允许，最后通过 MCP 通道执行，状态用 SSE 的 `tool_event` 推回前端。模型侧的决策交给 pi，我做的主要是上层控制面。

多轮状态我分了三层。最底下是持久化：用户消息、专家回复、工具调用记录都落库，系统提示词不从专家表实时查，而是读任务行上冻结的 JSON 快照。中间是并发纪律：同一轮还在流式输出时，如果同任务又来一条消息，直接 429 加 Retry-After，保证同一时刻只有一轮在推进状态；任务外还有一个容器总量限制，防止资源被打满。最上面是连续性：每个容器有一个重播种标记，新容器收到的第一条消息会先从库里取最近一段历史，嵌到消息开头，保证重建后的容器和第一次调用时的提示词、方法论是一致的。

这部分我讲得比较顺，因为确实是亲手踩过的东西。

## 第三问：上线后出过什么问题

第三个问题问的是：请介绍一次 AI 应用上线后出现的效果、性能或稳定性问题，说明怎么定位、采取什么措施、最终结果。

我停在这里。

倒不是答不上来。我在第一问已经说过，这个项目没有公网上线。一个正常的面试官听到这里，应该会改问本地联调或者压测阶段的问题，而不是照着原题继续要“上线后的故障复盘”。再加上前两个问题的形状——先要项目介绍，再要架构细节，最后要一份完整的故障复盘——拼起来很像一份课程大纲。

我当时的第一反应是：对方可能在套方案。于是没有继续往下讲。

## 聊完去查了公司

聊完我顺手查了一下工商信息。公司 2026 年 7 月 1 日成立，注册资本 3 万，员工人数 0，注册在粤港澳大湾区的一个孵化基地。经营范围里除了人工智能应用软件开发，还有业务培训、教育咨询、数字内容制作。

看到这里，我的判断反而没那么确定了。

一种解释还是“在采集内容”：AI 培训业务最缺的就是真实项目的架构和踩坑复盘，Q2 的四个技术点加 Q3 的复盘结构，确实很像课件大纲；Q3 和“没有公网上线”的前提冲突却没被纠正，也说明对方可能没在认真听。

但另一种解释也成立：这家公司本身就在做 AI 培训和课程内容，而我的实习岗位恰好是 AI 课程研发，负责教材实验和课程主线项目。如果它要招的是一个“既能做 AI 工程、又能把工程讲成课”的人，那三个问题就不是套方案，而是在看我会不会把自己的项目讲清楚。线上不方便看代码，让人口述架构是最快的验证方式。

我没法凭一次聊天给这家公司定性。能确定的是：在对方说清岗位、团队和后续流程之前，我不该继续输出更细的实现细节。这个止损线跟对方是不是在套方案无关。

## 回头核对，发现自己也有几处说法不准

写这篇的时候我翻了一下项目档案，发现当场有几个数字和表述需要改：

- 重播种历史我说的是 30 条，档案里两处都写 40 条。这个数字得查代码钉死，不能再靠记忆。
- 数据库我说“正在迁移到 pgSQL”，实际 V2 是在 PostgreSQL 16 上重建数据层，不搬 V1 数据。说“重建”比说“迁移”准确，也更能说明工作量。
- 简历里写的是 JWT 认证，但 V2 已经换成 opaque cookie + CSRF + Argon2id + TOTP。简历描述的是 V1，不算错，但如果对方顺着 JWT 往下问，我得能接住。
- “项目没有公网上线”是实话。更准确的说法是：公网部署设计已经完成，但受资源限制降级成了受限运行。

这些都不影响这次面试的判断，但会影响下一次。

## 最后留下几条

- **觉得不对就早停，但别用沉默代替表达。** 可以直接说：“这块涉及团队内部实现，不太方便展开，我们可以聊聊岗位职责和团队情况。”比不接话更好，也能顺便看对方是接住还是绕开。
- **Q3 可以纠题，不必硬答。** 没有生产事故就直说，然后把话题引到真实发生过的问题上，比如本地全链路联调时那个 1.17MB 单行 JSONL 触发 asyncio 64KB 行上限的问题，或者压测阶段的并发问题，问对方想听哪一类。不撒谎，也不浪费一次交流。
- **投递之后花几分钟查一下公司主体。** 成立时间、注册资本、员工人数、经营范围，不是为了给人下结论，而是决定自己该讲到什么深度。
- **线上面试的文字稿只是草稿。** 线上可以边想边改，线下是一口气说完的。把这次的回答当成素材，练成能在紧张状态下说出来的短句，才算真的准备好。

这次没有后续，也没有一个漂亮的结论。但它至少让我把“什么时候该停”和“没有上线该怎么讲”这两件事想明白了。下次再遇到类似的节奏，我希望能更早地把话题拉回岗位本身，而不是等到第三问才反应过来。
