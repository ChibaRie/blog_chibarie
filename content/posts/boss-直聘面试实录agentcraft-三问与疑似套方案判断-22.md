## 原始内容

2026-09-04，在 BOSS 直聘给一家公司投了简历：**广州她格人工智能科技**。

面试官连续问了三个问题，逐层深入。

### 第一问：项目介绍

> **面试官**：请结合一个您实际参与的 AI 应用项目，说明项目解决的问题、您负责的核心模块、采用的模型与技术栈，以及最终上线效果。

> **我的回答**：我拿实习期间作为核心负责人开发的 AgentCraft 多租户 Agent 工作台给您介绍下。
>
> 很多领域专家的经验散落在提示词、笔记中，很难沉淀和复用；普通使用者缺少已经封装完毕、开箱可用的专业智能体来解决各种垂直场景的问题。这个平台的价值就是轻量便捷地把专家能力集成，然后对外交付使用，可以将人设、方法论、Skill、MCP 工具打包成可发布的 AI 专家，并且支持用户自带密钥来调用。
>
> 我主要负责的模块是：
>
> 1. **Agent 的运行时**。基于 pi agent-core 作为 Agent 内核，没有自研 Agent 内核，基于它做上层平台二次开发。任务启动时注入人设、技能与工具配置，再以任务级快照冻结隔离配置的变更。
> 2. **SSE 流式链路**。调试了一些事件协议，打通 MCP 工具注册-授权-执行-回传这一条完整调用链路。
>
> 后端使用 FastAPI，ORM 用 SQLAlchemy、Alembic 做数据库版本管理，数据库是 SQLite，目前正在迁移到 pgSQL；前端是 React + Vite；容器化基于 Docker；测试用 pytest，Playwright 辅助我。我在开发和本地验证的时候有使用一些 coding agent 辅助我完成开发，跑通完整流程。
>
> 项目没有公网上线，是公司课程教材主线示范项目，交付目标是可复现 MVP 系统 + 配套实验材料。

### 第二问：RAG 与多轮状态

> **面试官**：在 RAG 或 Agent 项目中，您是如何处理文档切片、向量检索、重排、工具调用或多轮状态管理的？请结合实际方案说明。

> **我的回答**：我的项目不是 RAG 架构，所以切片、向量检索、重排没有做。
>
> **关于工具调用**：我基于 MCP 协议打通完整链路（http/stdio），先工具注册发现，读取 MCP 服务暴露出来的工具列表，可以将工具绑定到专家，然后在对话中真实调用。对话中，pi 负责解析大模型输出的工具调用请求，调用决策由模型决定；接着校验任务快照判断是否允许调用，允许后通过 MCP 通道执行工具，执行状态通过 SSE 以 `tool_event` 事件推到前端页面，用户可以看到「正在调用某某工具」。我利用 pi agent-core 内核负责模型侧的工具决策输出，我主要做的是上层控制面。
>
> **关于多轮状态管理**：分三层。
> - **一层持久化层**：用户的消息、专家的回复以及工具调用记录全部落库。系统提示词不从专家表查，而是从已冻结的任务行上读 JSON 快照。
> - **第二层并发纪律层**：当一轮回复还在 SSE 流式输出时，同任务再来一条消息直接 429 加 Retry-After，保证同一时刻只有一轮在推进状态——参考了各种 LLM 供应商限流时的 `429 too many requests`。在任务外有一个限制并发的容器总量，防止资源爆满。
> - **第三层是连续性层**：每个容器有一个重播种的标记，新容器收到的第一条消息，会先从库里取最近 30 条历史，并嵌入消息开头，保证每次重建的容器和第一次调用专家的方法论、提示词完全一致。

### 第三问：上线后的问题（我停在这里）

> **面试官**：请介绍一次 AI 应用上线后出现的效果、性能或者稳定性问题的经历，说明您如何定位原因，采取了什么措施，以及最终结果。

到这里，我意识到他可能在套我的方案，于是没有继续回答下去。按理来说，这种涉及专业技术的，应当在线下技术面的时候才会问到，这令我很费解。

不过这次对话也可以作为一次线下面试前的经验记录——因为如果我在线下，肯定没办法讲得这么详细具体，甚至会卡壳。

### 判断层

- **三个问题是一条设计过的梯度**：Q1 是标准开场（任何人都能答）；Q2 从通用问题切进架构细节（开始要求真东西）；Q3 要求「上线后的问题复盘」，而**我在 Q1 已经明确说过「项目没有公网上线」**。面试官在已知前提矛盾的情况下仍然按原问题往下问，说明这句话要么没被听进去，要么提问是按脚本走的。
- **Q2 一次抛出四个技术点**（切片/向量/重排/多轮状态），**Q3 直接要「定位原因 + 措施 + 结果」的完整复盘结构**——这是一份**内容大纲**的形状，不是一面试探的节奏。
- **但「套方案」不是唯一解释。** 抓住公司背景（见下）之后，出现了第二种同样合理、甚至更贴合的读法：**对方做的就是 AI 培训/教育业务，要的可能正是「能把 AI 工程项目讲成教材」的人——而我自己的实习岗位恰好就是「AI 课程研发实习生」。** 具体见「关键细节·一」的两种读法对比。
- **我停止回答是合理的止损**，但两种解释都无法凭一次对话定论。停手保护了方案资产，代价是可能放掉一个匹配度不错的岗位——这个代价需要用「先确认岗位信息」的方式补回来，而不是靠继续输出细节。

### 一·补：从「套方案」到另一种读法

拿到背景信息后，同一个事实序列可以有两种解释，两种都成立：

**读法 A：在采集内容（我的第一直觉）**

- AI 培训类业务最缺、也最值钱的素材，正是「真实项目的架构方案 + 上线踩坑复盘」。
- Q2 的四个技术点和 Q3 的复盘结构，拼起来接近一份课件大纲。
- Q3 与「项目没有公网上线」的前提冲突却没被纠正，说明对方没在认真听——这是最强的警示信号。

**读法 B：岗位本来就是「AI 工程 + 课程研发」的复合角色（同样合理）**

- 这家公司的业务是「AI 软件开发 + 业务培训 + 教育咨询」，**它需要的人本就是「既能做 AI 工程、又能把工程讲成教材」的角色**。
- 而**我的实习岗位恰恰就是「AI 课程研发实习生」，负责《AI Coding 与 Harness 工程》教材实验研发与课程主线项目**（见 dev 版简历实习经历）。从简历看，我与这个画像的匹配度很高。
- 在这个读法下，「你能不能把自己的项目讲清楚」就是**岗位核心能力的现场测试**，而不是套取方案。线上面聊不方便看代码，让对方口述架构是最快的验证方式。
- Q3 仍然可疑（前提矛盾没被纠正），但性质可能是「**提问走流程、没认真听**」，而不是「**有意图地套取**」。

**两种读法的分界点在哪：**

| 观察项 | 偏向 A（采集） | 偏向 B（真招） |
| --- | --- | --- |
| 是否给出岗位名称、职责、团队规模 | 含糊、绕开 | 能明确说清 |
| 是否关心我的到岗时间、薪资预期、职业规划 | 完全不问 | 一定会问 |
| 是否愿意进入下一轮（线下面试/笔试/看代码） | 止步于此 | 主动推进流程 |
| 是否追问「你个人」的判断与取舍 | 只关心方案本身 | 会问「为什么这么选」「你怎么想的」 |

**结论**：现阶段两种解释的权重接近，**不要急着给对方定性**。最省成本的做法是下一次沟通时**主动把话题拉回岗位本身**（岗位职责是什么、团队几个人、接下来的流程怎么走），对方的反应会直接给出答案——这也是「可复用点」第 4 条给出的那句话术的实际用途。

**唯一已经确定的判断**：在对方说清岗位与流程之前，**不必继续输出更细的实现细节**。这个止损线设得对，与对方是否在套方案无关。

### 二、Q3 那个问题的真正问题在哪

Q3 要求「上线后出现的效果/性能/稳定性问题」。它有三个隐性问题：

1. **前提冲突**：我在 Q1 说过「项目没有公网上线」。一个真实评估者的正常反应是改问——「那本地验证/压测阶段碰到过什么性能问题？」，而不是照原题继续。
2. **信息价值最高**：「上线后出的问题 + 怎么定位 + 什么结果」，等价于**别人花了几周踩出来的坑的一次性交付**。这类内容在技术社区是硬通货，在培训场景是卖点。
3. **它对我其实是不利题**：项目确实没有生产上线，我没有真实的生产故障可讲。硬答只能编，或者把本地环境的问题包装成「上线问题」——**这才是真正的风险点**，因为一旦包装，后面的追问就失控了。

所以「答不上来」不是能力缺口，是**这道题与事实不匹配**。真正的正确应对不是沉默，而是**当场把题面纠回来**，见「可复用点」第 3 条。

### 三、本次自述 vs 项目档案：三处口径需要统一

`input/materials/2026-09-10-164200-agentcraft-project-material.md` 是本项目的第一手事实源。把这次面试的口头表述逐条拉回去核对：

**① 重播种历史条数：30 条 vs 40 条（必须改）**

- 我说：「新容器收到的第一条消息，会先从库里取最近 **30 条**历史」
- 档案写：`_reseed_message`，**「最近 40 条历史嵌入首条消息」**；决策 #5「无会话持久 + 内存连续 → 重播种最近 **40 条**历史」

两处档案口径一致，都写 40。**我说的 30 是唯一的孤本**，且是个会被当场追问、且一查就露的数字。**改口为 40，或核对代码后统一。**

**② 数据库迁移的说法：「正在迁移到 pgSQL」（表述过软）**

- 我说：「数据库是 SQLite，目前正在迁移到 pgSQL」
- 档案写：V2 是**渐进改造·分层重建**，数据层属「**重建**」类（SQLite → PostgreSQL 16，30 表分四域），且**明确不迁移 V1 数据**——PostgreSQL 从全新 `0001` 基线开始，`agentcraft.db` 被判定为「开发联调数据，无生产价值」。

「迁移」在面试语境里容易被理解成「搬数据」，而实际动作是**在 PG 上重建数据层、抽象层重写**。更准确且更有分量的说法是：

> 「V1 是 SQLite，V2 我们没搬数据，而是在 PostgreSQL 16 上重建了数据层——30 张表分四域，带 RLS 和双 DB role 授权矩阵。」

这句话同时点出 RLS 和双 role，比「正在迁移」的信息密度高一个量级。

**③ 项目归属：面试说法与简历一致 ✅，错的是项目档案**

先说结论：**面试里说的「实习期间作为核心负责人开发的」「公司课程教材主线示范项目」，与 dev 版简历完全对得上，没问题。**

**为什么这仍然是个必须修的问题：**

1. **以后每次打开这份档案做面试准备，都会拿到一个错误的前提**。这次面试的表述之所以经得起核对，是因为简历和记忆是对的；但档案是知识库里唯一的「第一手事实源」，它错了就会污染后续所有推导（比如写输出、做准备笔记时会照抄「自研项目」）。
2. **「自研」和「公司项目」的追问方向完全不同**：说自研，要被问个人动机、投入时间、为什么做这个选型；说实习单位的课程主线项目，要被问**团队规模、我在几人团队里的位置、是否独自负责、教材评审流程、公司为什么选这个方案**。「核心负责人」这个身份，会被直接追问「团队几个人、你管什么、决策权到哪」——这些答案现在都得从零准备。

**④ 附带发现：「项目没有公网上线」（可改成更有分量的说法）**

我说「项目没有公网上线」——档案里有 V2 受邀多租户公网 Beta 的设计，但硬约束条目写「用户 VM 128GiB 磁盘不足 → 部署阶段按 Ops §2 降级条款（并发 1、暂停公网开放在线）」。所以「没有公网在线」是**准确**的，更精确的说法是「已完成公网部署设计，但受资源限制降级为受限运行」——这个版本听起来更专业，且仍是实话。

**⑤ 附带发现：简历写「JWT 认证」，但 V2 已经不用 JWT 了**

- dev 版简历：「实现 **JWT 认证**、专家/Skill 状态机……」
- 档案：V2 的认证与会话属于「**重建**」类，从「JWT + localStorage」改为「**opaque cookie + CSRF + Argon2id + TOTP**」

简历描述的是 **V1 的实现**，本身不算错，但如果面试官顺着 JWT 往下问（比如「JWT 没法主动失效你怎么处理」），需要用「V2 已经换成 opaque cookie + CSRF，就是因为 JWT 在这几点上不合适」来接——**这其实是个很好的加分点，前提是先意识到简历停在 V1 口径**。这一条 2026-09-11 的核对笔记没有覆盖，是本次新发现。

### 四、线上线下答题能力的落差，本身就是一条可训练项

我自己的判断是准的：**线上能讲这么细，线下大概率会卡**。

原因不是紧张，而是**线上文字沟通允许「边组织边输出」**——可以停顿、可以改口、可以把长句拆开发。线下面试是**单次不可编辑的口语流**，要求是：结构先于内容（先说框架，再填细节）、语速不等于思考速度、被追问时不慌。

这次的三段话其实是**一次免费的答案采集**：它们是在低压力环境下产出的、接近完整的版本。正确用法是把它当**草稿**处理，而不是当战果——打磨成能在压力下脱口而出的结构版本。

## 可复用点

1. **每道 AI 岗的技术初面，都会问这三个问题**：项目介绍（Q1）→ 方案深挖（Q2）→ 故障复盘（Q3）。这次已经拿到了 Q1、Q2 的完整答案，Q3 需要**另找素材**（见第 3 条）。
2. **Q2 的答题结构可以复用**：先明确「我的项目不是 RAG 架构，所以切片/向量/重排没做」——**主动排除不适用的部分，比硬凑答案更显专业**；然后分点答「工具调用」和「多轮状态管理」，后者用「持久化 / 并发纪律 / 连续性」三层拆解。这个三层结构是这次回答里最像样的部分。
3. **Q3 的正确答法是纠题，不是沉默**：把「没有生产上线」转化为可讲的东西——
   > 「这个项目没有生产上线，所以没有真实的生产事故。但有两类真实问题我可以讲：一是本地全链路联调时踩到的传输层缺陷（1.17MB 单行 JSONL 触发 asyncio 64KB 行上限，修复方案是把传输层 limit 提到 32MiB 并与上游同源）；二是压测/验收阶段的并发与资源问题。您想听哪一类？」
   这个答法有三个好处：不撒谎、把话题引到自己有货的地方、并且当场验证对方到底是评估还是在采集。
4. **停手的判断标准**：当对方在**没有给出岗位信息**的前提下，连续追问实现细节到第 3 层，且问题与已提供的事实前提冲突时，就该停。这不是不礼貌，是保护自己的方案资产。**注意**：制止的表述可以更干脆——「这块涉及团队内部实现，具体细节不太方便展开，我们可以聊聊岗位本身的职责和团队情况」。比沉默更好，因为**它把球踢回去，顺带完成了对对方的判别**（接住 = 大概真在招人；绕开 = 大概率在采集）。
5. **先核对方主体，再决定输出深度**：查工商信息只要几分钟（成立时间、注册资本、员工数、经营范围、注册地址）。**成立 < 半年 + 员工 0 人 + 经营范围含培训/咨询**，这类主体的「面试」需要多一层警惕；反过来，**经营范围与我的项目形态重合**本身就是重要信号。这个核查动作应该固化成投递后的常规步骤。
6. **知识库的「事实源」自己也会错，要定期和简历对拉**：这次核对最有价值的发现不是面试答错了什么，而是**项目档案把「实习单位的课程主线项目」记成了「自研项目」**。档案是知识库里唯一的项目事实源，它错了会污染后续所有推导（写准备笔记、写输出、做 Spark 关联时都会照着错的前提走）。**每次改简历或准备面试前，把档案和简历对拉一遍**，比事后补救便宜得多。
7. **把这次的三段回答存成草稿，不要存成定稿**：目标是产出「线下面试版」——结构更硬、句子更短、能在紧张状态下复述。
8. **同一个判断要有两个解释再下结论**：这次我第一反应是「套方案」，抓到公司经营范围后才意识到「对方业务是 AI 培训，而我的实习岗位就是 AI 课程研发，匹配度其实很高」。单一解释很容易变成情绪化的自我叙事，两个解释并列才逼出真正的判别动作（把话题拉回岗位，看对方反应）。
